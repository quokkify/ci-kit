# Composite actions

This toolkit now ships reusable composite actions for common setup and runtime patterns.

Executable examples use full commit SHA pins with release comments (`@<40-character SHA> # vX.Y.Z`). Renovate manages these through its native GitHub Actions manager, including `examples/`. Documentation and Copier version answers continue to use release tags. Examples demonstrate the API available in their pinned release; tests exercise new outputs against the current source before release.

- `actions/checkout/action.yml`
  - centrally pinned checkout with upstream inputs and `ref`/`commit` outputs; see [checkout migration and delivery](../docs/checkout.md)
- `actions/setup-python/action.yml`
  - setup-python with dependency cache and install handling
- `actions/setup-node/action.yml`
  - setup-node with package-manager detection and cache
- `actions/setup-java-gradle/action.yml`
  - setup-java with dependency/JDK caching and Gradle wrapper validation
- `actions/gradle-retry/action.yml`
  - runs a trusted Gradle command with bounded repository HTTP 403/429 backoff and one `--refresh-dependencies` recovery attempt for repository not-found failures; unrelated `Forbidden`, HTTP 500, and ordinary failures are not retried
- `actions/compose-up/action.yml`
  - validates safe Compose/profile/hook inputs, delegates one startup lifecycle to the standalone health action, and optionally waits for HTTP readiness
- `actions/deploy-gh-pages-subdir/action.yml`
  - compatibility wrapper in toolkit `v2.6.0` that forwards the unchanged input contract once to immutable standalone `gh-pages-subdir-action` `v0.1.1` (`816d85aa756f480457befb42168633cb6ccf09c7`) and remains input-compatible for migration.
- `actions/gradle-problems-summary/action.yml`
  - summarizes workspace-contained Gradle Problems Reports as an escaped, bounded job-summary table with problem counts as outputs
- `actions/junit-step-summary/action.yml`
  - safely aggregates bounded, workspace-contained JUnit XML globs into a GitHub job-summary table and numeric outputs
- `actions/allure-report/action.yml`
  - compatibility wrapper that forwards the Allure 3 HTML/badge/PR-comment contract once to standalone `allure-report-action` `v0.5.3` (`00a2788fd72dce6727a3232104f770f659aeaccb`), including provenance-aware merging, provenance-scoped module environments, and the compact status summary comment

Consumers call these from their own jobs when they need the setup/runtime sequence without delegating the complete job to a reusable workflow. Run the shared checkout action before these setup actions; in particular, `setup-java-gradle` must see the checked-out caller repository so its default wrapper validation can scan repository-contained `gradle-wrapper.jar` files. The toolkit reusable workflows keep equivalent setup steps inline because their checkout is the caller repository, not this toolkit repository. Contract tests keep their setup behavior and defaults aligned with these actions.

`allure-report` delegates unchanged inputs to [`quokkify/allure-report-action`](https://github.com/quokkify/allure-report-action). Its default `source-artifacts-directory: auto` uses provenance-aware merge and attribution when complete `ci-env-fragment.properties` sidecars are present, and otherwise preserves compatible already-merged results. By default, a `module` result label creates separate Allure environments and scopes matching variables to those environments; set `module-environment-label` to an empty value to disable this behavior. Tests without an `epic` label remain in overall totals: Playwright is classified as `E2E`, while otherwise unclassified results appear under `No epic assigned`. The wrapper preserves `docs/testing/test-pyramid.md` as the default policy link; callers can provide another path or leave it empty. Pass `github-token: ${{ secrets.GITHUB_TOKEN }}` and grant `pull-requests: write` in both public and private repositories. GitHub Pages is optional and disabled by default; enable it only with `contents: write` and a destination directory. The hidden comment marker is configurable so repositories do not overwrite one another's report comments.

The Python and Node actions install dependencies by default. Set `install-dependencies: "false"` for runtime-only setup. The Java/Gradle action uses setup-java v6 for dependency and JDK caching, includes Gradle properties in cache inputs, and validates repository-contained Gradle Wrapper JAR files by default; set `cache-dependencies: "false"` or `cache-jdk: "false"` to disable either cache independently. It deliberately leaves dependency and build commands to the caller. Inputs such as `install-command` are trusted workflow configuration; never construct them from pull-request titles, branch names, or other untrusted event data.

pnpm and modern Yarn projects must pin the package-manager version in `package.json` with `packageManager` (for example, `pnpm@10.0.0` or `yarn@4.0.0`). Yarn Classic lockfiles use the action's pinned Yarn 1 compatibility version. This avoids Corepack selecting an environment-dependent known-good release.

These setup actions are project setup recipes, not drop-in replacements for every upstream input/output. Use upstream actions directly when you need their full interface. The setup/cache/install sequences support Linux and macOS runners; other operating systems are not covered by the toolkit's validation. Runtime-only setup with no package-manager preparation requires both `install-dependencies: "false"` and `cache-dependencies: "false"`.

Node and Python cache only the selected package manager's actual cache directories. Keys include the runner OS/architecture, resolved runtime version, package-manager name/version, and dependency manifest hashes. Node explicitly disables setup-node's automatic npm cache so `cache-dependencies` controls the only cache mechanism. Poetry caches downloaded artifacts and repository metadata, not virtual environments. Existing cache entries receive a cold miss on the first run after this change.

For pnpm and Yarn, setup installs the exact `corepack-version` into a temporary directory and enables its shims before restoring caches or installing dependencies. This also works with Node versions that no longer bundle Corepack. The default Corepack 0.34.0 requires Node 20.10+, 22.11+, or 24+; older Node projects must choose a compatible Corepack version. npm projects do not install Corepack. Yarn Classic uses the pinned 1.22.22 fallback when the project does not specify a package-manager version.

Python's built-in uv and Poetry installers use the interpreter selected by setup-python and expose the resulting virtual environment through `GITHUB_PATH` and `VIRTUAL_ENV` for later steps. Plain `python`, `pytest`, and the reusable workflow's default test command therefore use the installed project environment. uv honors its project environment location; Poetry honors its environment configuration and must have virtualenv creation enabled. A custom `install-command` owns tool installation and environment activation; it bypasses built-in project-tool preparation and uses only the base pip/npm cache. Export custom environment changes through GitHub's environment files when subsequent steps need them.

`setup-java-gradle` returns a shell-escaped `gradle-project-command` containing the absolute wrapper path (or `gradle`) and `--project-dir`. Pass it through an environment variable to Bash, for example `bash -euo pipefail -c "$GRADLE_COMMAND test"`, where `GRADLE_COMMAND` is `${{ steps.java.outputs.gradle-project-command }}`. It works from any directory, including for nested projects and paths containing spaces. The existing `gradle-command` output retains its workspace-relative executable path for compatibility; it does not select the project directory. Prefer the new output for nested projects and treat it as a Bash command. `gradle-retry` also accepts `working-directory`; callers using relative commands for nested projects must pass it explicitly.

`junit-step-summary` is self-contained and framework-neutral. Call it with `if: always()` after the test command, because GitHub otherwise skips a later step when an earlier test step fails. `junit-paths` accepts newline-delimited paths or `*`, `?`, and `**` globs relative to `working-directory`; `**` must be a complete path segment, consecutive `**` segments are collapsed, and at most four remain. Literal path prefixes prune unrelated trees before a linear directory-fd walk. The action deduplicates files, does not follow symlinks, and bounds directory depth, scanned entries, matched files, per-file bytes, and aggregate bytes. It rejects traversal, DTD/entity declarations, malformed counts/durations, and unsafe file replacements, then exposes canonical suite totals through outputs without changing the underlying test command's result. Missing reports warn by default; set `fail-on-missing: "true"` when the report is mandatory. The action requires Python 3.9 or newer on a POSIX runner and no repository write permissions or secrets.

For a staged migration from the original CSP-local action, deprecated `cwd` plus `variant` inputs remain accepted together and map `frontend-single`, `backend-pytest`, and `e2e-playwright` to their historical report paths. New consumers must use `working-directory` plus `junit-paths`; do not mix the two contracts. CSP should use `fail-on-missing: "true"` while migrating so a wrong path cannot silently produce zero totals.

`gradle-problems-summary` surfaces the [Gradle Problems Report](https://docs.gradle.org/current/userguide/reporting_problems.html) in the job summary. Gradle writes one incubating HTML report per build invocation, in the root project's `build/reports/problems/problems-report.html`, and only when the build reports problems such as deprecations or compiler warnings; a missing report therefore usually means a clean build and is not an error by default. Call the action with `if: always()` after the Gradle step:

```yaml
- name: Summarize Gradle problems
  if: ${{ always() }}
  uses: quokkify/ci-kit/actions/gradle-problems-summary@<40-character SHA> # vX.Y.Z
  with:
    report-paths: |
      build/reports/problems/problems-report.html
      tools/*/build/reports/problems/problems-report.html
```

`report-paths` uses the same workspace-contained `*`, `?`, and complete-segment `**` globs and the same scan, file-count, per-file, and aggregate byte bounds as `junit-step-summary`; symlinks and traversal are rejected. Each matched report gets its own section, appended after any earlier summary content, with one row per problem id and severity: severity, problem, group, first message, first location (workspace-relative when possible, otherwise the task path), and the occurrence count including occurrences Gradle summarized without listing them. Rows across all reports are capped by `max-rows` and the appended Markdown by `max-summary-bytes`. Set `fail-on-missing: "true"` when the build must produce a report. Outputs are `reports`, `invalid-reports`, `problems`, and `has-problems`; the action never changes the Gradle step's result.

Report content is untrusted in pull-request builds. The action reads only the JSON between the `// begin-report-data` and `// end-report-data` lines that Gradle embeds in the report, parses it with the Python standard library as data, and never executes or renders the report's HTML, scripts, or links. Every field is stripped of control and formatting characters, collapsed to one line, truncated, HTML-escaped, and Markdown-escaped before it reaches the summary, and URL schemes and `www.` prefixes get a zero-width space so GitHub does not autolink them; workflow-command output escapes paths as well. The format was verified against reports generated by Gradle 9.5.1 and 9.8.2; it is incubating and may change between releases, so a report without that data block or without a `problemsReport` section (for example a configuration-cache report) is reported as unsupported with a warning instead of failing the job. Python 3.9 or newer must be available on a POSIX runner; the action needs no repository write permissions or secrets.

`compose-up` v2 is intentionally a thin wrapper. `compose-files`, `before-compose-hook`, and `after-health-hook` are relative to `working-directory`; paths are validated and prefixed before delegation so Compose derives its project directory from the first normalized file and hooks remain workspace-contained. `profiles` is normalized and forwarded to both Compose and the lifecycle hooks. The before hook can export Compose interpolation values; the after hook can run project-specific readiness/bootstrap checks. When `services` is explicit, `completed-services` is appended as a stable, unique union; when `services` is empty, the standalone action retains its default coverage of all configured services, including successful one-shots. `additional-compose-args` is forwarded to the standalone startup command and defaults to empty; callers can explicitly pass options such as `--quiet-pull`. `build` appends `--build`, and `timeout-seconds` maps to the standalone timeout. `wait-for-health: "false"` and `show-logs-on-failure: "false"` fail closed because the pinned standalone release owns those semantics. HTTP readiness is checked after the standalone action succeeds. With `down-on-timeout: "true"`, a failure after confirmed Compose startup runs a scoped `docker compose down` command with the same files and profiles, without `-v`; normal cleanup remains caller-owned.
